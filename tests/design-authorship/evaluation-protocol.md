# Design Authorship Behavioral Evaluation

This protocol supports the candidate changes derived from [the v0.2.0 implementation plan](../../docs/plans/design-authorship-v0.2.0.md). It is an evaluation guide, not a runtime requirement for every design task.

## Separate the Claims

- Package and catalog checks establish valid packaging, discoverable references, and consistent evaluation inputs.
- Decision exercises establish how an independently prompted agent handles the supplied situations.
- Rendered artifact exercises establish only the inspected layouts, states, and behaviors.
- User preference, observed attention, and broader improvement require their own evidence. None follows from passing the other checks.

## Independent Decision Exercises

Give an evaluator only the candidate skill and realistic requests or raw fixtures. Keep expected behaviors, release records, proposed fixes, and prior responses out of its context. Select cases from `evaluation-scenarios.yaml` by the changed behavior; do not pass the answer fields to the executing agent.

Review its response against the supplied task and evidence. Include a small repair and legitimate card collection so anti-default guidance cannot pass by enforcing more ceremony or fewer rectangles. Include an existing design owner, an unaccepted trial, and evidence challenging an accepted layout so continuity cannot pass by freezing every prior choice.

## Bounded Maintenance Exercise

Use a temporary, explicitly synthetic project with an accepted design owner and a standalone source artifact. Preserve the initial source so later comparisons have a stable reference. Keep generated outputs and execution logs outside the canonical repository.

1. Ask the agent to implement an ordinary extension with an existing task, visual language, supported layouts, and delegated local choices.
2. Inspect the actual result and execute affected actions, including a failure and recovery if relevant. Record visual evidence with its source identity, viewport, and state.
3. Give a subsequent maintenance request or actual finding, preserving the same accepted project direction. Do not supply the desired fix.
4. Check whether the second result improves the target and preserves unaffected relationships. Check documentation against verified behavior: temporary work, accepted intent, and intentional evolution must not become competing current baselines.

Useful checks include context before and after selection, proximity of feedback to its action, repeated operations, long content, narrow layout, keyboard continuity, and role consistency across surfaces. Select checks according to the actual change rather than requiring every state in every exercise.

Look for these failures:

- a feature inventory becomes an equal-card page without task-based grouping;
- removing card borders leaves the same fragmented attention structure;
- notes, panels, or errors hide the current object or next meaningful action;
- cosmetic improvements change the meaning of color, boundaries, or emphasis elsewhere;
- the newest screenshot or code silently replaces accepted intent;
- a demonstrated baseline defect is preserved solely for consistency;
- an agent claims observed gaze, usability-study results, or general aesthetic gains from synthetic inspection;
- the maintained document promises states or validation that were never exercised.

## If Comparing Versions

Use matched content, tasks, settings, tools, and comparable effort. Preserve both outputs, randomize presentation labels for human visual comparison, and record failures as well as successes. A single candidate exercise does not establish an improvement over v0.1.2; repeated representative trials are needed for reliability claims.

Record a concise result in the version evidence with the actual source identity and scope. Keep model responses and generated artifacts out of the runtime package. Stop after the agreed checks or a real unresolved boundary; do not run a fixed aesthetic-score loop.
